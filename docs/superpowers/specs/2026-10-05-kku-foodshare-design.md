# KKU FoodShare — แบบระบบสำหรับพัฒนาต่อ

วันที่: 5 ตุลาคม 2026

สถานะ: ร่างแบบระบบสำหรับตรวจทาน ยังไม่ใช่รายงานว่าพัฒนา ทดสอบ หรือ deploy สำเร็จ

## 1. เป้าหมายและสิ่งที่ตกลงแล้ว

พัฒนาเว็บไซต์ KKU FoodShare จากโปรเจกต์ที่ผู้ใช้แนบมาให้ใช้งานได้ครบวงจร ตั้งแต่สมัครสมาชิก โพสต์อาหารพร้อมรูปและพิกัด จองอาหาร ไปยังจุดรับ และยืนยันการส่งมอบ ใช้ได้ทั้งโทรศัพท์และโน้ตบุ๊ก พร้อมชุดติดตั้งและ deploy ที่ทำซ้ำได้

สิ่งที่ผู้ใช้ระบุ:

- อนุญาตให้แก้ไขทุกส่วนเพื่อให้ใช้งานได้จริง สวยงาม และสะดวก
- ต้องโพสต์ได้จริงและปักหมุดตำแหน่งได้จริง
- เลือกแบบ A: จองอาหารผ่านเว็บไซต์ ระบุจำนวน และมีประวัติการรับ
- ใช้ใบงานรายวิชา CP353002 เป็นข้อกำหนดประกอบ

ค่าเริ่มต้นที่เสนอและแก้ไขได้ในการตรวจทานครั้งนี้:

- เว็บภาษาไทย ชุมชนหลักคือผู้ใช้รอบมหาวิทยาลัยขอนแก่น
- แบ่งปันอาหารฟรี ไม่มีระบบชำระเงินหรือจัดส่ง
- รับสมัครด้วยอีเมลทั่วไป ไม่บังคับโดเมนมหาวิทยาลัย เพราะยังไม่มีข้อกำหนดดังกล่าว
- ผู้ใช้บัญชีเดียวเป็นทั้งผู้แบ่งปันและผู้รับได้ แต่จองโพสต์ของตัวเองไม่ได้
- จองแล้วกันจำนวนทันที ไม่ต้องรอเจ้าของอนุมัติ
- เจ้าของโพสต์เป็นผู้ยืนยันการส่งมอบหลังตรวจรหัสรับอาหารจากผู้รับ
- คงชื่อ โลโก้ และมาสคอตเดิม ปรับรูปแบบหน้าเว็บและการนำทางให้สอดคล้องกัน
- ส่งมอบซอร์สโค้ดและชุด deploy; URL สาธารณะต้องใช้บัญชีโฮสต์และการตั้งค่าจริงของผู้ใช้ก่อนยืนยันว่าออนไลน์

## 2. สิ่งที่พบในโค้ดปัจจุบัน

ตรวจจากซอร์สใน ZIP ยังไม่ได้ยืนยันด้วยการรันระบบ:

- มี Spring Boot, Maven, Java 17, Thymeleaf, Spring Security และ PostgreSQL
- มีโค้ดสมัครสมาชิก เข้าสู่ระบบด้วยรหัสผ่าน/Google รีเซ็ตรหัสผ่าน และรูปโปรไฟล์
- แผนที่ Leaflet อ่านข้อมูลจาก `GET /api/food-posts/map` และมีการขอตำแหน่งปัจจุบัน
- FoodPost service ทำหน้าที่อ่านโพสต์สำหรับแผนที่ ยังไม่มีวงจรสร้าง แก้ไข ลบ หรือจอง
- ปุ่มแบ่งปันหลายตำแหน่งเป็นลิงก์ `#`; รายการอาหารและสถิติบางส่วนเขียนค่าตายตัว
- พบ entity สำหรับ 4 ตาราง: users, food_posts, user_profile_images, password_reset_tokens
- ยังไม่พบ Dockerfile, Compose, migration, Swagger/OpenAPI configuration หรือเอกสารระบบที่ครบตามใบงาน

## 3. แนวทางสถาปัตยกรรม

### แนวทางที่เลือกเสนอ

ปรับปรุงระบบเดิมเป็น Spring Boot application เดียว แสดงหน้าด้วย Thymeleaf และใช้ JavaScript สำหรับแผนที่ การค้นหา รูปตัวอย่าง และการโต้ตอบกับ REST API ฐานข้อมูลใช้ PostgreSQL

เหตุผล: ใช้ฐานโค้ดเดิมต่อได้ แยกหน้าที่ตามใบงาน ลดการตั้งค่า deploy หลายระบบ และยังทำ responsive UI ได้เต็มรูปแบบ

ทางเลือกที่พิจารณา:

| ทางเลือก | ข้อดี | สิ่งที่ต้องแลก |
|---|---|---|
| Spring Boot + Thymeleaf เดิม | ใช้โค้ดเดิมต่อ จัดการ session และ deploy ในแอปเดียว | ส่วนโต้ตอบซับซ้อนต้องจัด JavaScript เป็นโมดูลอย่างมีระเบียบ |
| Spring Boot API + React แยกส่วน | เหมาะเมื่อทีมต้องการพัฒนา frontend แยกเป็นผลิตภัณฑ์ | ต้องเขียนหน้าส่วนใหญ่ใหม่ เพิ่มงาน auth, build และ deploy |

ขอบเขตการพึ่งพา: Controller → Service interface → Repository → Entity และแยก DTO/Mapper, Security, Validation, Exception ออกจากกัน Controller ไม่เรียก Repository โดยตรง

เลือก dependency รุ่นที่มีอยู่จริงและเข้ากันได้หลังตรวจ build เดิม ไม่อ้างว่ารุ่นใน pom.xml ใช้งานได้ก่อนทดสอบ

## 4. ผู้ใช้และสิทธิ์

| บทบาท | การใช้งาน |
|---|---|
| ผู้เยี่ยมชม | อ่านหน้าแนะนำ ดูรายการ/รายละเอียดอาหารและแผนที่ ไม่เห็นข้อมูลติดต่อส่วนตัวหรือรายละเอียดการจอง |
| สมาชิก | สร้าง/จัดการโพสต์ของตนเอง จองอาหาร ดูการจองและการแจ้งเตือน แก้ไขโปรไฟล์ รายงานโพสต์ |
| เจ้าของโพสต์ | ดูรายการจองเฉพาะโพสต์ของตน ยืนยันส่งมอบด้วยรหัสรับอาหาร ปิดหรือยกเลิกโพสต์ตามกติกา |
| ผู้ดูแลระบบ | ดูสรุป ตรวจรายงาน ซ่อนโพสต์ที่มีปัญหา ระงับบัญชี พร้อมบันทึกผู้ดำเนินการและเหตุผล |

ตรวจสิทธิ์ฝั่ง server ทุกครั้ง ไม่อาศัยการซ่อนปุ่มเพียงอย่างเดียว บัญชีผู้ดูแลสร้างผ่านขั้นตอนตั้งค่าที่ระบุชัดเจน ไม่มีรหัสผ่านเริ่มต้นที่เผยแพร่ใช้ได้บน production

## 5. หน้าจอและทิศทางการออกแบบ

ธีมหลักพื้นอ่อน ตัวอักษรเข้ม ใช้ฟ้า/เขียวจากแบรนด์เดิมเป็นสีหลัก คงมาสคอตเฉพาะส่วนที่ช่วยสร้างเอกลักษณ์ หน้าใช้งานจริงเน้นรูปอาหาร จำนวนคงเหลือ เวลารับ และการกระทำหลัก

หน้าจอที่ต้องมี:

1. หน้าแนะนำ พร้อมปุ่มค้นหาอาหารและเริ่มแบ่งปัน
2. หน้าค้นหา แสดงรายการและแผนที่ สลับมุมมองได้ กรองประเภท คำค้น และช่วงเวลาที่รับได้
3. รายละเอียดอาหาร: รูป ข้อมูลอาหาร สารก่อภูมิแพ้ถ้าผู้โพสต์ระบุ จำนวน หน่วย เวลารับ จุดนัดพบ และปุ่มจอง
4. สร้าง/แก้ไขโพสต์: อัปโหลดรูป กรอกรายละเอียด เลือกช่วงเวลา และปักหมุด
5. โพสต์ของฉัน: แก้ไข ปิดรับ ดูการจอง และยืนยันส่งมอบ
6. การจองของฉัน: จำนวน สถานะ รหัสรับอาหาร จุดรับ ปุ่มนำทาง และยกเลิก
7. โปรไฟล์/ตั้งค่าบัญชี
8. การแจ้งเตือนในเว็บ
9. หน้าผู้ดูแล: รายงานปัญหา โพสต์ และบัญชี
10. หน้าเข้าสู่ระบบ สมัครสมาชิก ลืม/ตั้งรหัสผ่านใหม่ และหน้าข้อผิดพลาด

มือถือใช้ navigation ด้านล่างสำหรับ ค้นหา แผนที่ โพสต์ การจอง และบัญชี ส่วนโน้ตบุ๊กใช้แถบนำทางด้านบน พื้นที่กดหลักไม่น้อยกว่า 44px ฟอร์มมี label และ error ข้างช่อง รองรับ keyboard และแสดง focus ชัดเจน

ทุกหน้ามีสถานะกำลังโหลด ไม่มีข้อมูล สำเร็จ และผิดพลาด ไม่มีปุ่มที่แสดงเหมือนใช้งานได้แต่ไม่ทำงาน ไม่มีตัวเลขผลลัพธ์หรือรายการจำลองปะปนกับข้อมูลจริง

## 6. วงจรโพสต์และการจอง

### โพสต์อาหาร

- ระบุชื่อ ประเภท รายละเอียด จำนวนทั้งหมด หน่วย รูปหลัก จุดรับ พิกัด และช่วงเวลารับ
- เวลาสิ้นสุดต้องหลังเวลาเริ่ม และยังไม่ผ่านไปแล้ว; แสดงเวลา Asia/Bangkok
- เก็บ timestamp ให้มีความหมายชัดเจนและแปลงเขตเวลาที่ขอบเขตระบบ
- เก็บจำนวนทั้งหมดกับจำนวนส่งมอบแล้ว ส่วนจำนวนกันไว้คำนวณจากการจองที่ยังมีผล
- จำนวนที่จองได้ = จำนวนทั้งหมด − จำนวนส่งมอบแล้ว − จำนวนที่กันไว้
- หมดจำนวนที่จองได้เพราะถูกจองครบต้องแสดง “จองเต็ม” ต่างจาก “รับครบแล้ว”
- เจ้าของลดจำนวนรวมให้ต่ำกว่าจำนวนที่ส่งมอบแล้วบวกจำนวนที่จองอยู่ไม่ได้
- หลังมีการจอง ไม่อนุญาตเปลี่ยนจุดรับหรือช่วงเวลารับ หากต้องเปลี่ยนให้ยกเลิกโพสต์พร้อมแจ้งผู้จอง แล้วสร้างใหม่
- ลบโพสต์แบบเก็บประวัติ: รายการจะหายจากการค้นหาสาธารณะ แต่ยังคงการจองและบันทึกกิจกรรม
- การปิด/ลบโพสต์ยกเลิกการจองที่ยังไม่รับทั้งหมดใน transaction เดียว และแจ้งผู้จอง

### การจอง

1. ผู้ใช้เข้าสู่ระบบ เปิดรายละเอียดอาหาร และเลือกจำนวนจำนวนเต็มที่เป็นบวก
2. server ตรวจว่าโพสต์เปิดรับ ไม่หมดเวลา ไม่ใช่เจ้าของโพสต์ และมีจำนวนเพียงพอ
3. ใช้ transaction กับการล็อกแถวโพสต์ ป้องกันการจองพร้อมกันแล้วเกินจำนวน
4. สร้างการจองสถานะ RESERVED กันจำนวน และออกเลขอ้างอิงพร้อมรหัสรับอาหาร
5. ผู้รับเห็นการจองใน “การจองของฉัน” และเจ้าของเห็นใน “โพสต์ของฉัน”
6. ผู้รับไปยังจุดรับภายในช่วงเวลา และแสดงรหัสให้เจ้าของ
7. เจ้าของกรอกรหัสเพื่อยืนยันส่งมอบ server ตรวจรหัส สิทธิ์ สถานะ และเวลา แล้วเปลี่ยนเป็น COLLECTED
8. เพิ่มจำนวนส่งมอบเพียงครั้งเดียว และคงประวัติให้ทั้งสองฝ่าย

### กติกาเพิ่มเติม

- หนึ่งบัญชีมีการจองที่ยังมีผลได้หนึ่งรายการต่อหนึ่งโพสต์ ลดความสับสนจากการกดซ้ำ
- เปลี่ยนจำนวนรายการ RESERVED ได้เมื่อมีสต็อกเพียงพอ โดยตรวจภายใต้ lock เดียวกัน
- ผู้รับยกเลิกได้ก่อนส่งมอบหรือหมดเวลา; คืนจำนวนเพียงครั้งเดียว
- เมื่อหมดเวลารับ การจอง RESERVED เปลี่ยนเป็น EXPIRED และห้ามยืนยันรับย้อนหลัง
- มี scheduled cleanup แต่ทุกการเขียนข้อมูลตรวจเวลาเองด้วย ไม่พึ่ง job เพียงอย่างเดียว
- คำขอซ้ำต้องไม่ทำให้จำนวนลด/เพิ่มซ้ำ ใช้สถานะปัจจุบันร่วมกับ idempotency key สำหรับสร้างการจอง
- ล็อกทรัพยากรในลำดับเดียวกันทุกเส้นทาง เพื่อลด deadlock
- รหัสรับอาหารสุ่มด้วยตัวสร้างที่เหมาะสม เก็บค่าแฮช จำกัดความถี่การลอง และไม่แสดงให้ผู้ใช้อื่น

| สถานะการจอง | เปลี่ยนต่อได้เป็น | ผู้ทำได้ |
|---|---|---|
| RESERVED | COLLECTED | เจ้าของโพสต์ เมื่อรหัสถูกและอยู่ในช่วงรับ |
| RESERVED | CANCELLED | ผู้จอง / เจ้าของเมื่อปิดโพสต์ / ผู้ดูแลเมื่อจัดการโพสต์ |
| RESERVED | EXPIRED | ระบบ เมื่อเกินเวลารับ |
| COLLECTED / CANCELLED / EXPIRED | ไม่มี | อ่านประวัติได้ แต่ไม่เปลี่ยนกลับ |

## 7. แผนที่และรูปภาพ

ใช้ Leaflet ที่มีอยู่ในโปรเจกต์ต่อ แยก map module สำหรับเลือกจุดรับกับแสดงจุดอาหาร

- แตะ/คลิกแผนที่เพื่อวางหมุด ลากหมุดเพื่อปรับ แล้วแสดงพิกัดและชื่อจุดรับให้ตรวจ
- ปุ่มใช้ตำแหน่งปัจจุบันทำงานเมื่อผู้ใช้กดขอเท่านั้น หากปฏิเสธสิทธิ์ยังปักหมุดด้วยมือได้
- จุดตั้งต้นของแผนที่อยู่บริเวณมหาวิทยาลัยขอนแก่น ไม่ใช้เป็นพิกัดโพสต์อัตโนมัติโดยไม่มีการยืนยัน
- ตรวจ latitude/longitude ทั้ง frontend และ backend
- ชื่อจุดรับเป็นข้อความที่ผู้ใช้กรอกได้ ไม่ผูกการสร้างโพสต์กับบริการค้นหาที่อยู่ภายนอก
- “ใกล้ฉัน” คำนวณระยะทางจากพิกัดโดยระบุว่าเป็นระยะโดยประมาณ ไม่ใช่ระยะขับรถ
- เปิดนำทางไปยังพิกัดจริงด้วยลิงก์ Google Maps
- tile provider ตั้งค่าผ่าน environment ได้ แสดง attribution และตรวจเงื่อนไขผู้ให้บริการก่อน deploy
- ถ้าโหลดแผนที่ไม่ได้ ยังแสดงชื่อจุดรับ พิกัด และลิงก์นำทางในรายละเอียดได้

รูปภาพตรวจชนิดจากเนื้อหา จำกัดขนาด/จำนวนพิกเซล ไม่รับไฟล์ executable หรือ SVG จากผู้ใช้ สร้างชื่อไฟล์ใหม่ บีบอัดรูป และเก็บใน persistent storage ไม่ฝังลงในโฟลเดอร์ build ชุด Docker ใช้ volume; โฮสต์หลาย instance ต้องใช้พื้นที่เก็บไฟล์ร่วมกันผ่าน storage interface

## 8. ฐานข้อมูลที่เสนอ

| ตาราง | หน้าที่ | ความสัมพันธ์หลัก |
|---|---|---|
| users | บัญชี รหัสผ่าน บทบาท สถานะ | 1:N posts, reservations, notifications |
| user_profile_images | รูปโปรไฟล์ | 1:1 users |
| password_reset_tokens | token รีเซ็ตรหัสผ่าน | N:1 users |
| food_posts | รายละเอียดอาหาร จำนวน ช่วงเวลารับ และพิกัด | N:1 users |
| food_post_images | metadata รูปอาหาร | N:1 food_posts |
| reservations | ผู้จอง จำนวน สถานะ รหัสรับ และเวลา | N:1 food_posts และ users |
| notifications | แจ้งเหตุการณ์และสถานะอ่านแล้ว | N:1 users |
| reports | รายงานปัญหาโพสต์และผลการตรวจ | N:1 food_posts และ users |
| audit_events | บันทึกการจัดการที่สำคัญ | อ้างอิงผู้ดำเนินการและทรัพยากร |

ใช้ Foreign Key, unique constraint, check constraint สำหรับจำนวน และ index สำหรับการค้นหา/เจ้าของ/การจอง/สถานะอ่าน เลือก LAZY เป็นค่าเริ่มต้นของความสัมพันธ์ที่เหมาะสม และไม่ cascade ลบบัญชีไปยังประวัติการส่งมอบ

ใช้ Flyway สำหรับ schema และ migration ข้อมูลตัวอย่างเป็น profile แยกที่ไม่เปิดบน production การนำฐานข้อมูลเดิมมาใช้ต้องสำรองและตรวจ schema จริงก่อนใช้ migration; ไม่มีคำสั่ง drop หรือ clean ที่ทำงานโดยปริยาย

## 9. REST API

ฐาน URL `/api/v1` แยก Request DTO และ Response DTO ไม่ส่ง entity, password hash, token hash หรือข้อมูลติดต่อของผู้อื่นออกไป

| Resource | การทำงานหลัก |
|---|---|
| /food-posts | สร้าง ค้นหาแบบแบ่งหน้า กรอง และเรียงลำดับ |
| /food-posts/{id} | อ่าน แก้ไข ลบแบบเก็บประวัติ |
| /food-posts/{id}/images | จัดการรูปโดยเจ้าของ |
| /food-posts/map | จุดอาหารที่ยังรับจองได้ภายในขอบเขตแผนที่ |
| /food-posts/{id}/reservations | สร้างการจอง และรายการจองที่เจ้าของมีสิทธิ์เห็น |
| /reservations/{id} | อ่าน แก้ไขจำนวน และยกเลิกแบบเก็บประวัติ |
| /reservations/{id}/collection | ยืนยันส่งมอบโดยเจ้าของ |
| /me/reservations | การจองของผู้ใช้ปัจจุบัน |
| /me/posts | โพสต์ของผู้ใช้ปัจจุบัน |
| /me/notifications | การแจ้งเตือนและอ่านแล้ว |
| /reports | รายงานโพสต์ |
| /admin/* | จัดการรายงาน บัญชี และโพสต์ โดยผู้ดูแล |

Food posts และ Reservations เป็นสอง resource หลักที่มี Create/Read/Update/Delete ครบ โดย Delete ของการจองหมายถึงยกเลิก ไม่ลบประวัติ

มี Bean Validation, Global Exception Handler และรูปแบบ error เดียวกัน ใช้ HTTP status ตามเหตุการณ์ เช่น 201 เมื่อสร้าง, 204 เมื่อลบ/ยกเลิกตาม contract, 400 ข้อมูลไม่ถูกต้อง, 401 ยังไม่เข้าสู่ระบบ, 403 ไม่มีสิทธิ์, 404 ไม่พบ, 409 จำนวนไม่พอ/สถานะขัดแย้ง

Swagger UI อธิบาย authentication, CSRF, ตัวอย่างข้อมูลและ error; หน้าเว็บจริงใช้ API หรือ service contract ที่สอดคล้องกัน

## 10. บัญชีและการแจ้งเตือน

- คง session authentication และ CSRF protection สำหรับการแก้ไขข้อมูล
- normalize อีเมลและบังคับ unique แบบไม่แยกตัวพิมพ์ใหญ่เล็ก
- Google Login เปิดได้เมื่อมี credentials ถูกต้อง หากไม่ตั้งค่า ระบบหลักยังเริ่มทำงานและใช้ email/password ได้
- ตรวจความน่าเชื่อถือของอีเมลจากผู้ให้บริการก่อนผูกบัญชี
- รีเซ็ตรหัสผ่านใช้ token ครั้งเดียว มีอายุ จำกัดคำขอ และตอบแบบไม่เปิดเผยว่ามีบัญชีนั้นหรือไม่
- SMTP เป็น integration ที่ต้องตั้งค่าจริงก่อนยืนยันว่าอีเมลส่งถึงผู้ใช้ได้ ไม่แสดงผลสำเร็จปลอม
- การแจ้งเตือนในเว็บบันทึกลงฐานข้อมูล ไม่ขึ้นกับบริการส่งอีเมล
- ข้อมูลลับย้ายไป environment variables; ไม่รวมค่าจริงลงในตัวอย่าง config หรือเอกสาร
- ใช้ cookie setting และ proxy configuration ที่เหมาะกับ HTTPS บน production
- output ข้อความจากผู้ใช้ผ่าน escaping และจำกัดขนาดข้อมูลทุกจุดที่รับเข้า

## 11. Design Patterns และเอกสารตามใบงาน

คง Layered Architecture, MVC, Repository, Service Layer, DTO + Mapper และ Constructor Injection

เลือก GoF กลุ่ม Behavioral อย่างน้อย 3 แบบโดยมีปัญหาจริงรองรับ:

| Pattern | ปัญหาที่แก้ | หน่วยที่ออกแบบ |
|---|---|---|
| Strategy | เรียง/คัดเลือกอาหารตามเกณฑ์หลายแบบโดยไม่รวมทุกทางเลือกใน controller | FoodDiscoveryStrategy และตัวเลือกใกล้ฉัน/หมดเวลาก่อน |
| Observer | หลังจอง ยกเลิก ส่งมอบ หรือปิดโพสต์ ต้องสร้างการแจ้งเตือนโดยไม่ให้ controller ทำทุกอย่าง | Reservation/FoodPost events และ notification listeners |
| State | จำกัดการเปลี่ยนสถานะการจองและป้องกันคืนจำนวนหรือยืนยันรับซ้ำ | Reservation state transition policies |

เขียน `doc/solid-analysis.md` และ `doc/design-patterns.md` อ้างอิงไฟล์/บรรทัดจากโค้ดที่ส่งมอบจริง พร้อม Use Case, Domain/Class, Sequence อย่างน้อย 3 scenario, Activity, ER, Component, Deployment และ State diagrams

README มีวิธีติดตั้ง รัน ทดสอบ API และ deploy ส่วนรายชื่อสมาชิก รหัสนักศึกษา branch และหลักฐานการทำงานใช้ข้อมูลจริงจากทีม ไม่สร้างข้อมูลแทนผู้ใช้

โฟลเดอร์ส่งมอบครบ code/, test/, doc/, img/ พร้อมคู่มือและโครงสไลด์อธิบายระบบที่สร้างขึ้น ไม่มีการแต่งประวัติ commit, ผู้เขียน หรือผลทดสอบ

## 12. การทดสอบและเกณฑ์รับงาน

### สิ่งที่ต้องทดสอบ

- Unit tests กติกาจำนวน เวลารับ สิทธิ์ การยกเลิก และการเปลี่ยนสถานะ
- Integration tests กับ PostgreSQL สำหรับ migration, transaction และการจองพร้อมกัน
- API tests ตรวจ validation, CSRF, role/ownership และ error contract
- ทดสอบ flow ผ่านหน้าเว็บจริงตั้งแต่สมัคร/เข้าใช้ → โพสต์และปักหมุด → บัญชีอื่นจอง → เจ้าของยืนยันรับ
- ตรวจ responsive ที่ความกว้าง 360, 390, 768 และ 1366px รวม navigation, modal, form และ map
- ตรวจ build, startup, health check และข้อมูลยังอยู่หลัง restart

### ตัวอย่างผลที่ต้องได้

| กรณี | ผลที่คาดหวัง |
|---|---|
| โพสต์ 5 กล่อง จอง 2 | จำนวนจองได้เหลือ 3 |
| ยกเลิก 2 ที่ยังไม่รับ | กลับมาจองได้ 5 ไม่เพิ่มซ้ำเมื่อส่งคำขอซ้ำ |
| 2 คนแย่งจองอาหารชิ้นสุดท้าย | สำเร็จได้เพียง 1 คน อีกคนได้ข้อความจำนวนไม่พอ |
| ผู้ใช้แก้โพสต์คนอื่น | ถูกปฏิเสธจาก server |
| พิกัดหรือช่วงเวลาไม่ถูกต้อง | ไม่บันทึกและแสดง error ที่แก้ไขได้ |
| ปฏิเสธ GPS | ยังโพสต์ด้วยการปักหมุดเองได้ |
| จองครบแต่ยังไม่รับ | แสดงจองเต็ม ไม่เพิ่มสถิติส่งมอบ |
| ยืนยันรับซ้ำ | จำนวนและสถิติไม่เพิ่มซ้ำ |
| เลยเวลารับ | จองใหม่และยืนยันส่งมอบไม่ได้ |
| ฐานข้อมูล/บริการภายนอกขัดข้อง | แจ้งความผิดพลาดตามจริง ไม่สร้างรายการสำเร็จจำลอง |

รายงานการตรวจจะแยก “รันผ่านจริง”, “ยังไม่ได้รัน” และ “ติดข้อจำกัดสภาพแวดล้อม” ห้ามใช้เพียงการอ่านโค้ดแทนหลักฐานว่าระบบใช้งานได้ครบ

## 13. Deploy และสิ่งส่งมอบ

- Dockerfile แบบ build และ runtime แยกขั้นตอน พร้อม non-root runtime
- docker-compose.yml สำหรับแอป PostgreSQL และ persistent upload volume
- environment example ที่ไม่มี secret, health check, migration และคู่มือ backup/restore
- คู่มือตั้งค่า hostname, HTTPS, datasource, upload storage, SMTP และ Google OAuth callback
- GitHub Actions สำหรับ build/test; deploy automation ต้องผูกกับโฮสต์จริงก่อนเปิดใช้
- ซอร์สโค้ดที่แก้ไขแล้ว รายงานทดสอบ เอกสารระบบ และคำสั่งเริ่มใช้งานที่ตรวจสอบได้

คำว่า “พร้อม deploy” หมายถึงเตรียมและตรวจขั้นตอน build/configuration/startup ตามหลักฐานที่ทำได้ ส่วนคำว่า “deploy แล้ว” ใช้เมื่อมี URL สาธารณะและตรวจการทำงานบน URL นั้นจริงเท่านั้น

## 14. ลำดับงานหลังแบบระบบได้รับการทบทวน

1. ตรวจ build baseline, dependency compatibility และ config ของระบบเดิม
2. จัด schema/migration, auth, validation และ error contract
3. พัฒนาโพสต์ รูปภาพ แผนที่ และการค้นหา
4. พัฒนาการจอง การยืนยันรับ การแจ้งเตือน และกติกาจำนวน/เวลา
5. ปรับหน้าเว็บทุก flow และผู้ดูแลให้สอดคล้องกัน
6. ทดสอบ integration, concurrency และ responsive แล้วแก้ปัญหาที่พบ
7. จัด Docker, เอกสาร, รายงานหลักฐาน และแพ็กชุดส่งมอบ

ไม่รวมแชทเรียลไทม์ การชำระเงิน แอปมือถือแบบ native หรือระบบจัดส่ง เนื่องจากไม่จำเป็นต่อวงจรแบ่งปันอาหารที่ตกลงไว้
